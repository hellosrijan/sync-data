124	    row, created = Outbox.objects.get_or_create(

144	## 2. Outbound task (build-plan phase 5)
145	
146	New file `src/sync/tasks.py` (Dramatiq actors; this is what `<app>/tasks.py` discovery in
147	`CLAUDE.md` is for).

149	```python
150	@dramatiq.actor(max_retries=0)          # the outbox drives retries, not Dramatiq (design §6, Q7)
151	def send_outbound():
152	    now = timezone.now()
153	    for row in Outbox.objects.select_for_update(skip_locked=True).filter(
154	            state=Outbox.State.PENDING, next_attempt_at__lte=now
155	    ).order_by("next_attempt_at"):
156	        with transaction.atomic():
157	            row.lease_until = now + timedelta(seconds=60)
158	            row.save(update_fields=["lease_until"])
159	        _send_one(row)   # reads CURRENT field values at send time, not a stored snapshot (Architecture)
160	```
161	
162	- **`SKIP LOCKED`** is why two worker processes never fight over the same row — the loop body
163	  must run inside its own short transaction per row, not one transaction for the whole batch,
164	  or `SKIP LOCKED` can't do its job.
165	- **Current values, not a snapshot:** read `getattr(record, field)` for each name in
166	  `row.fields` right before sending — this is what makes several merged edits collapse into one
167	  call and makes a retried send harmless (Architecture, "We send the current value").
168	- **Outcome handling** (5.3.2), one `match`/`if` block in `_send_one`:
169	
170	  | Outcome | Action |
171	  |---|---|
172	  | accepted | `row.state = SENT`; `row.sent_at = now`; on a create, `record.salesforce_id = <returned id>; record.save()` |
173	  | unreachable / timeout / 5xx | `row.attempts += 1; row.next_attempt_at = now + min(2**row.attempts, 60)s; row.lease_until = None` |
174	  | 429 | same as above but also call the limiter's slow-down (below); honour `Retry-After` if present |
175	  | 400-type (bad data) | `row.state = NEEDS_REVIEW; row.last_error = <message>` — never deleted (Q9) |
176	  | 401/403 | stop the whole task early and raise/alert — don't keep burning the rate limit on calls that will all fail |
177	
178	- **Wake-up:** `transaction.on_commit(lambda: send_outbound.send())` wherever `apply()` (or the
179	  portal view) commits a change that touched the outbox, **plus** a crontab job
180	  (`dramatiq_crontab`, `@interval(seconds=5)`) that calls `send_outbound.send()` unconditionally
181	  as a backstop for a lost wake-up (5.3.3). The task itself is idempotent (it only sends rows
182	  that are actually due), so calling it extra times is harmless.

184	## 3. Shared rate limiter (5.2)
185	
186	One Redis key, one Lua script (atomic token bucket), used by **every** caller: sends, retries,
187	the probe, and catch-up queries. Put it in `src/sync/limiter.py`.
188	
189	- State in Redis: current allowed rate (starts at `settings.SALESFORCE_RATE_LIMIT`) and a token
190	  count, refilled continuously.
191	- `limiter.acquire(timeout=...)` blocks (or the caller re-queues) until a token is free.
192	- On a 429: `limiter.throttle()` halves the current rate immediately, then a crontab job
193	  (`@interval(seconds=30)`) adds 5 req/s back, capped at the configured limit, until it's
194	  recovered.
195	- Test with `redis-py`'s real client against the Redis the compose stack already runs — no
196	  need to mock Redis for this.

198	## 4. Down detection and probe (5.4)
199	
200	`SyncState` row `key="salesforce"`, `value={"status": "up"|"down", "consecutive_failures": N}`.
201	
202	- Every outbound failure classified as "unreachable" increments `consecutive_failures`; any
203	  success resets it to 0.
204	- At 5, set `status="down"`. While down, `send_outbound` should skip sending (checked at the
205	  top of the task) so it doesn't burn attempts against a Salesforce that's confirmed down.
206	- A separate crontab actor, `@interval(seconds=10)`, does a cheap probe call. On success:
207	  `status="up"`, `consecutive_failures=0`, then **run catch-up before anything else** (next
208	  section), then let `send_outbound` resume on its own next tick.

210	## 5. Catch-up (build-plan phase 6)
211	
212	`src/sync/tasks.py`, another actor, `run_catchup()`:
213	
214	1. Read `SyncState.key="watermark"` (a timestamp); subtract a few minutes of overlap.
215	2. Query the Salesforce client for "changed since T", 2,000 records/page, through the limiter
216	   (6.1.1).
217	3. For each record returned, build a `Change(source="salesforce", event_id=f"{record_id}:{modified_at}", ...)`
218	   and call `apply()` (6.1.2). The echo check in `apply()` is **field-level** (compares each
219	   field's `sf_value`, same code path as a webhook) — don't add a record-level "skip if last
220	   modified by us" shortcut; it would skip real changes that happened before our own edit in
221	   the same record.
222	4. Advance the watermark to the latest `modified_at` seen **only after that page's transaction
223	   commits** (6.1.3) — so a crash mid-page re-reads the same page instead of skipping it.
224	5. Triggered by the probe's success (step above) and by a `@interval(minutes=5)` safety net
225	   (6.1.4). Both call the same function; it's idempotent because `apply()` already is.

45	        customer = CustomerFactory()

47	        results = []
48	
49	        def worker(change):
50	            barrier.wait()                      # make both threads reach the lock at once
51	            results.append(apply(change))
52

55	        t1.start(); t2.start(); t1.join(); t2.join()
