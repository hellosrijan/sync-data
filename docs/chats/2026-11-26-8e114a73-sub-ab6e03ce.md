1	# sync-data
2	
3	Two-way sync of customer and contact records between Salesforce (the client's CRM) and the
4	Tequity operations portal (Postgres). Salesforce calls us with webhooks; we call the Salesforce
5	record API from a background worker, capped at 100 requests/sec. Design targets: 5 million
6	records, a 30-second sync window while both sides are up, and surviving a 6-hour Salesforce outage.
7	The brief is in [`docs/Round1.html`](docs/Round1.html).
8	
9	Status: phase 0 (project skeleton only, no models or sync logic yet).
10	
11	## Stack
12	
13	- Python 3.14, [uv](https://docs.astral.sh/uv/)
14	- Django 5.2 LTS, Django REST Framework
15	- Postgres 17 (portal database), Redis 7 (Dramatiq broker for the outbound worker)
16	- django-dramatiq, django-environ
17	
18	## Prerequisites
19	
20	- uv 0.13+ (installs Python 3.14 for you)
21	- Docker with Docker Compose v2
22	
23	## Setup
24	
25	```sh
26	cp .env.example .env          # then set DJANGO_SECRET_KEY and POSTGRES_PASSWORD
27	uv sync                       # creates .venv and installs dependencies
28	docker compose up -d --build --wait   # Postgres, Redis and the worker
29	uv run python src/manage.py migrate
30	uv run python src/manage.py runserver
31	```
32	
33	The server listens on http://127.0.0.1:8000. `GET /health/` returns 200 when Postgres and Redis
34	both answer.
35	
36	### Worker
37	
38	The `worker` container runs two processes:
39	
40	- `manage.py rundramatiq --reload --reload-use-polling --processes 1 --threads 2`, which
41	  executes Dramatiq actors and restarts when a `.py` file under `src/` changes (`src/` is
42	  bind-mounted).
43	- `manage.py crontab` (dramatiq-crontab), which enqueues actors decorated with `@cron(...)` /
44	  `@interval(...)`. A Redis lock keeps it to one scheduler.
45	
46	If either process exits, the container exits and `restart: unless-stopped` brings both back.
47	`docker compose logs -f worker` shows a heartbeat line every minute when both are healthy.
48	
49	Put actors in `<app>/tasks.py`; both commands discover them automatically. After changing
50	dependencies, rebuild with `docker compose up -d --build worker`.
51	
52	All configuration comes from `.env` (see `.env.example`). Docker Compose reads the same file, so
53	the Postgres credentials and ports are defined once.
54	
55	## Layout
56	
57	```
58	src/
59	  manage.py
60	  config/      Django project: settings, urls, wsgi/asgi
61	  sync/        the sync app
62	  utils/       shared bits: /health/ endpoint, rundramatiq override (fixes --reload)
63	docs/          brief and design notes
64	docker-compose.yml   Postgres + Redis + worker; Django's web server runs on the host
65	Dockerfile           worker image (uv, Python 3.14)
66	```
67	
68	## Stopping
69	
70	```sh
71	docker compose down           # keeps data in the named volumes
72	docker compose down -v        # also deletes the volumes
73	```

610	<section class="section reveal" id="background-and-scenario"><div class="wrap"><header class="section-head"><div class="kicker"><i class="ph ph-buildings" aria-hidden="true"></i></div><h2 class="heading-2">Background and scenario</h2></header><div class="section-body"><p class="body-3 measure">A client runs its sales team in Salesforce, a customer relationship management (CRM) product. Tequity has built the client an operations portal. Finance and customer-success staff work in the portal.</p><p class="body-3 measure">The same people exist in both places, as customers and as contacts. A sales person creates a customer in Salesforce. The portal should show that customer. A finance person on the portal then corrects the billing city. Salesforce should show the new city. Later, a sales person changes the phone number in Salesforce. The portal should show the new phone, and the city the finance person set should still be there.</p><p class="body-3 measure">The client also needs the history. They need to know who changed the phone, and who changed the city. The fact of an earlier edit stays on record after a later edit.</p><p class="body-3 measure">Salesforce stores its own copy. The portal stores its copy in PostgreSQL (Postgres). The two copies have to stay in sync. We are designing and building our side. Salesforce already exists, and it stays as it is.</p></div></div></section>
611	<section class="section reveal" id="the-systems-involved"><div class="wrap"><header class="section-head"><div class="kicker"><i class="ph ph-share-network" aria-hidden="true"></i></div><h2 class="heading-2">The systems involved</h2></header><div class="section-body"><p class="body-3 measure">Three parties matter.</p><ol class="cards cols-3 wide"><li><div class="body-3"><strong>Salesforce.</strong> The client's CRM. Sales users edit records here. Salesforce has its own database.</div></li><li><div class="body-3"><strong>The portal.</strong> Our application. Finance and customer-success users edit records here. Our database is Postgres.</div></li><li><div class="body-3"><strong>The network between them.</strong> Salesforce and the portal talk over the public internet, using Hypertext Transfer Protocol Secure (HTTPS). Each side keeps its own database. HTTPS is the only path between them.</div></li></ol><p class="title-3 measure">Who calls whom:</p><ul class="list list-ul measure"><li><div>When a record changes in Salesforce, Salesforce calls us. The call is a webhook: an HTTPS request to an endpoint we host. The webhook names the record and describes the change.</div></li><li><div>When a record changes in the portal, we call Salesforce. The call uses Salesforce's official record application programming interface (API): the create and update operations Salesforce already documents. The portal reaches Salesforce through that record API.</div></li><li><div>A sales user talks only to Salesforce. A portal user talks only to the portal. Neither user talks to the other system.</div></li></ul><p class="body-3 measure">The rate limit below applies to the requests we send to Salesforce. Webhooks Salesforce sends to us sit outside that cap.</p><div class="frame frame-diagram measure"><pre><code> Sales user                         Finance / customer-success user
612	     |                                          |

614	     v                                          v
615	 Salesforce CRM                           Tequity portal

A call to the Salesforce record API is a request we initiate. Salesforce may accept it, reject it, or be unreachable.</p></div></div></section>
630	<section class="section reveal" id="requirements-and-scale"><div class="wrap"><header class="section-head"><div class="kicker"><i class="ph ph-list-checks" aria-hidden="true"></i></div><h2 class="heading-2">Requirements and scale</h2></header><div class="section-body"><p class="title-3 measure">Records:</p><ul class="list list-ul measure"><li><div>Customers and contacts. About these fields, and no others, for this exercise: customer name, status, and owner; contact full name, phone, email, city, owner, and the customer they belong to.</div></li><li><div><strong>5 million records</strong> in production, customers and contacts counted together.</div></li></ul><p class="title-3 measure">Sync:</p><ul class="list list-ul measure"><li><div>While both systems are up, a create or an update on either side is visible on the other side within <strong>30 seconds</strong>. Thirty seconds is the worst case. Everyday sync should land sooner.</div></li><li><div>Both sides may create. Both sides may update.</div></li><li><div>The current value of a field is the one we can justify. The earlier values, who made them, and when, stay on record. 647	<section class="section reveal" id="constraints"><div class="wrap"><header class="section-head"><div class="kicker"><i class="ph ph-barricade" aria-hidden="true"></i></div><h2 class="heading-2">Constraints</h2></header><div class="section-body"><p class="body-3 measure"><strong>Rate limit.</strong> At most 100 requests per second to the Salesforce record API. The cap counts the calls we make, including retries. Webhooks arriving at our endpoint sit outside this cap. If Salesforce tells us to slow down, we slow down, and we keep the work.</p><p class="body-3 measure"><strong>Outages.</strong> Design for the Salesforce API being unreachable for <strong>6 hours</strong>. Webhooks Salesforce tried to send during that window may never arrive. Pending calls to Salesforce must still be there after our own process restarts.</p><p class="body-3 measure">Thirty seconds applies while both systems are up. Catch-up after an outage is a different target. Drain the backlog as fast as the rate limit allows. Compute how long that takes, in minutes, for the edit rate you assumed. Show the division.</p><p class="body-3 measure"><strong>Consistency.</strong> Two people may edit the same record at the same time, on the same side or on opposite sides. Edits to different fields of that record both have to survive. Edits to the same field need one current value and a kept history.</p><p class="body-3 measure">Say what you use to decide which edit is current, on a webhook and on a portal save. Name the field. If you need an API this note does not give you, mark it as an assumption.</p><p class="body-3 measure"><strong>Out of scope for this weekend:</strong> deletes, Salesforce login screens, a visual user interface, a second region, and a load test against real Salesforce. If you write a program, call a fake CRM you write yourself.</p></div></div></section>
