111	  - **Query API:** where we ask "which records changed since time T?". The brief doesn't promise this exists, so it's labelled *assumption, Q3*.
112	- **Bottom box: the Tequity portal.** Everything here is ours.
113	
114	Only the three **thick arrows, (A), (B) and (C)**, cross between the boxes, all over HTTPS. That's the brief's rule: "HTTPS is the only path between them." Everything else in the bottom box stays on our own network.
115	
116	The two people on the left mark the brief's other rule: a **sales user** only touches Salesforce, and a **finance / customer-success user** only touches the portal. Neither ever uses the other system. Every bit of syncing between them is our job.
117	
118	### 2. Inside the portal
119	
120	Inside the portal box there are three smaller boxes, plus Redis and `apply()` sitting loose.
121	
122	**Django web**, the part that receives requests:
123	- **Webhook endpoint:** Salesforce calls this when a record changes. It validates the request (is it really from Salesforce, is the payload well-formed), then hands it to `apply()`.
124	- **Portal API:** finance users' edits arrive here. It also hands each edit to `apply()`.
125	
126	**`apply(change)`**, the large box in the middle. Every change enters the database through this one function, whether it came from a webhook, a portal user or a catch-up run. It runs in a single database transaction, so either all its writes happen or none do. It's drawn as one box because having one implementation is the point: duplicates, ordering, history and the loop rule are all decided in one place. Its steps are in section 4.
127	
128	**Postgres**, our database. It holds five things:
129	
130	| Table | What it holds | Why it exists |
131	|---|---|---|
132	| **Customer / Contact** | The current value of every field, plus *when* each field was last set and by which side | The per-field time is how we tell whether an incoming change is newer |
133	| **field_change** | Every change ever made: field, value, who, when, from which side, and whether it became current | The brief's history requirement. Rows are only added, never changed. |
134	| **change_event** | The ID of every change we've seen, kept 7 days | Duplicate detection: a second copy of an ID is ignored |
135	| **outbox** | Portal edits waiting to be sent to Salesforce | The pending work. It's on disk, so it survives restarts, and it's never dropped. |
136	| **watermark** | How far the last catch-up got | So the next catch-up only asks for what's new |
137	
138	**Redis**, just a doorbell. When a row lands in the outbox, Redis tells the worker "there's work". If Redis lost that message, no work would be lost, because the outbox in Postgres still holds the row. That's why it's labelled *wake-up signal* and not *queue*.
139	
140	**Dramatiq worker**, the background process that talks to Salesforce. It has three parts:
141	- **Outbound task:** sends pending outbox rows to Salesforce.
142	- **Catch-up task:** asks Salesforce what changed, after an outage and every 5 minutes as a safety net.
143	- **Shared rate limiter**, the hexagon. *Every* call we make to Salesforce goes through it: sends, retries and catch-up queries. It keeps the total at or under 100 per second. It lives in Redis so that all worker threads and processes share one count. Webhooks don't pass through it, because the brief says they don't count.
144	
145	### 3. The three paths
146	
147	#### Path (A): Salesforce → portal (webhook)
148	
149	*Sales user → Salesforce CRM ⇒(A)⇒ webhook endpoint → `apply()` → tables*
150	
151	1. A sales user changes a phone number in Salesforce.
152	2. Salesforce sends a webhook to our endpoint over HTTPS. It carries `eventId`, `recordId`, `occurredAt`, `changedBy` and `changedFields`.
153	3. The endpoint validates it and calls `apply()`.
154	4. `apply()` updates the current phone (if this change is the newest), writes a history row, and records the event ID.
155	5. **No arrow goes from this path to the outbox.** That's the sync-loop rule: anything that came *from* Salesforce is never sent *back* to Salesforce.
156	
157	It's fast (milliseconds), and it doesn't count against the rate limit.
158	
159	#### Path (B): portal → Salesforce (outbound)
160	
161	*Finance user → Portal API → `apply()` → outbox ··notify··› Redis → Outbound task → rate limiter ⇒(B)⇒ Record API*
162	
163	1. A finance user sets city = Noida.
164	2. The Portal API calls `apply()`, which saves the city, writes a history row, **and in the same transaction** adds an outbox row saying "send city = Noida to Salesforce". Because it's one transaction, we can never end up with the edit saved but the send forgotten, or the reverse.
165	3. The outbox nudges Redis (dotted *notify*), and Redis wakes the outbound task.
166	4. The outbound task reads the pending row (*reads pending*) and asks the rate limiter for permission.
167	5. The limiter lets it through, and the task calls the Record API (thick arrow **B**).
168	6. The dotted **result** arrow is Salesforce's answer:
169	   - **Accepted:** mark the outbox row sent. On a create, also store the new Salesforce ID.
170	   - **Rejected, "slow down" or unreachable:** keep the row and retry later, through the limiter, so retries count toward the cap.
171	
172	This is the only path that writes to Salesforce, and only portal edits feed it (the *portal edits only* label on the arrow into the outbox).
173	
174	#### Path (C): catch-up (portal pulls from Salesforce)
175	
176	*Catch-up task → rate limiter ⇒(C)⇒ Query API ··changed records··› Catch-up task → `apply()` (each record) + watermark*
177	
178	1. It's triggered when Salesforce comes back after an outage, and every 5 minutes as a safety net.
179	2. The task asks the Query API for records changed since the watermark (thick arrow **C**). This call also goes through the limiter.
180	3. Salesforce returns the changed records (dotted *changed records*), up to about 2,000 per call.
181	4. Each record goes through **the same `apply()`** as a webhook (*each record*). So if we'd already received a change by webhook, the copy is recognised and causes nothing new.
182	5. The task moves the watermark forward.
183	
184	This path exists because of one line in the brief: webhooks Salesforce tried to send during the outage "may never arrive". Without (C), sales-side edits made during those 6 hours would be lost for good.
185	
186	### 4. What happens inside `apply()`
187	
188	The box says *dedupe · lock · history · per-field newest wins · outbox*. In order:
189	
190	1. **Dedupe:** try to record the change's ID. If it's already there, this is a duplicate, so reply OK and stop.
191	2. **Lock** the record, so two simultaneous edits to it go one after the other instead of overwriting each other.
192	3. **Echo check:** if the change came from Salesforce and its `changedBy` is *our integration user*, it's our own update coming back. Record it and stop.
193	4. **For each field:**
194	   - always write a history row;
195	   - if the change is newer than that field's stored time, make it the current value;
196	   - if it's older, it stays in history only, marked *superseded*;
197	   - on an exact tie, Salesforce wins.
198	5. **Outbox:** if the change came from the portal and changed at least one field, add an outbox row.
199	6. **Commit**, so all of the above happens or none of it does.
200	
201	### 5. The brief's scenario, traced through the diagram
202	
203	| Step | Path | What happens |
204	|---|---|---|
205	| Sales creates a customer in Salesforce | **A** | The webhook creates the record; one history row per field |
206	| Finance corrects the billing city to Noida | **B** | `apply()` saves the city and adds an outbox row; the worker sends it to Salesforce through the limiter |
207	| Salesforce echoes our city change back as a webhook | **A** | Echo check: `changedBy` is our integration user, so it's recorded but not re-applied, and nothing goes back out. No loop. |
208	| Sales changes the phone | **A** | Only the phone is applied. The city is a different field, so *"the city the finance person set should still be there"* ✅ |
209	| Salesforce sends that phone webhook twice | **A** | The second copy hits the same event ID, so nothing happens |
210	| A late, older phone change arrives | **A** | History row saved as superseded; the current phone stays as it is |
211	| "Who changed the phone, who changed the city?" | — | Read from **field_change**: every edit, actor and time, including superseded ones |
212	
213	### 6. During and after a 6-hour outage
214	
215	- **While Salesforce is down:**
216	  - Portal edits keep working, because path B's first half (`apply()` → outbox) doesn't need Salesforce. Outbox rows pile up safely in Postgres.
217	  - The outbound task's calls fail; the rows stay pending, and a cheap test call every ~10 s checks whether Salesforce is back.
218	  - Webhooks (A) stop arriving.
219	- **When Salesforce comes back:**
220	  1. **Catch-up (C) first.** Pull what sales users changed during the outage and apply it. Conflicts on the same field are settled before we send anything.
221	  2. **Then drain the outbox (B)** as fast as the limiter allows. At the assumed 5 portal edits per second: 108,000 pending calls ÷ (90 − 5) per second ≈ **21 minutes**.
222	- **If our own process restarts during the outage:** nothing is lost. The pending work is in Postgres, not in memory or Redis.
223	
224	### 7. Reading the arrow styles
225	
226	| Style | Meaning |
227	|---|---|
228	| **Thick (A, B, C)** | Crosses the public internet over HTTPS. B and C count against the 100 req/s cap; A doesn't. |
229	| **Thin solid** | Data moving inside our system (writes, reads, hand-offs) |
230	| **Dotted** | Signals and replies: *notify*, *result*, *changed records* |
231	
232	## `apply(change)`: one function for every inbound change
233	
234	Webhooks (A), portal saves and catch-up results (C) all go through `apply()`. One
235	implementation covers duplicates, ordering, history and the loop rule.
236	
237	```
238	change = { source: salesforce | portal, event_id, record_id, occurred_at, actor, fields{...} }
239	
240	one Postgres transaction:
241	 1. Dedupe     INSERT event_id INTO change_event (unique). Conflict → duplicate: return OK.
242	 2. Lock       SELECT record ... FOR UPDATE   (serialises concurrent edits to one record)
243	 3. Echo       source = salesforce and actor = our integration user → our own update coming
244	               back: record it as a confirmation, apply nothing, stop.
245	 4. Per field  always INSERT field_change(record, field, value, actor, occurred_at, source)
246	               occurred_at > field's stored time → becomes current          (applied)
247	               otherwise → stays in history only                            (superseded)
248	               exact tie → Salesforce wins
249	 5. Outbox     source = portal and a field was applied → INSERT outbox row
250	               source = salesforce → never
251	 6. COMMIT
252	```
253	
254	Where the inputs come from:
255	
256	| Input | Webhook (A) | Portal save | Catch-up (C) |
257	|---|---|---|---|
258	| `event_id` | `eventId` | New UUID | `record_id` + Salesforce modified time |
259	| `occurred_at` | `occurredAt` | Our server clock when the save arrives | Salesforce modified time (record level) |
260	| `actor` | `changedBy` | The logged-in portal user | Salesforce "last modified by" |
261	| `fields` | `changedFields` | The fields in the form | Fields whose value differs from the last value we synced from Salesforce |
262	
263	## How the brief's rules are met
264	
265	| Rule | Mechanism |
266	|---|---|
267	| Duplicate webhook | `change_event.event_id` is unique, so a repeat is a no-op. IDs are kept 7 days. |
268	| Out-of-order change | Per-field `occurred_at` comparison. The older change is kept in history but isn't current. |
269	| Different fields edited at once | The comparison is per field, so both edits survive |
270	| Same field edited at once | The newest `occurred_at` is current, and every edit stays in history |
271	| History: who, what, when | `field_change` is written explicitly in `apply()` on every path, including superseded edits and bulk catch-up. It isn't a Django signal, because signals miss superseded edits and bulk writes. |
272	| Sync loop | Only portal edits create outbox rows. Our echo (actor = integration user) is never applied. |
273	| Pending calls survive restarts | The outbox row commits in the same transaction as the edit. Redis is only a wake-up signal, so losing it loses no work. |
274	| Slow down / unreachable | The outbox row stays pending and is retried through the limiter. It's never dropped (Q9). |
275	| Webhooks missed in the outage | Catch-up (C), triggered by recovery and every 5 min |
276	
277	## After an outage
278	
279	1. While Salesforce is down, outbound calls fail. Their outbox rows stay pending, and a probe
280	   checks every ~10 s whether Salesforce is back.
281	2. The probe succeeds, so Salesforce is back.
282	3. **Catch-up first.** Pull what changed in Salesforce since the watermark (minus a few minutes
283	   of overlap) and apply each record. Same-field conflicts are settled before we send anything.
284	4. **Then drain the outbox** at the full run rate. Edits to the same record are merged into one
285	   call.
286	
287	## Scale check
288	
289	*Assumptions* (recorded in [Design](Design) §1):
290	- **Q1:** peak 10 edits/s, split 5 Salesforce / 5 portal; working-hours average 3.5/s; quiet hour 0.2/s.
291	- **Q10:** run rate R = 90 req/s, leaving 10 for retries, probes and catch-up.
292	- **Q3:** the query API returns about 2,000 records per call.
293	- **Q12:** no bulk or mass updates.
294	
295	| Check | Arithmetic | Result |
296	|---|---|---|
297	| Salesforce changes missed in 6 h | 5/s × 21,600 s = 108,000 ÷ 2,000 per call | **54 calls**, under 1 s of cap |
298	| Outbox after 6 h | 5/s × 21,600 s = 108,000 calls at most (fewer once merged) | — |
299	| Drain, worst case (6 h of peak) | 108,000 ÷ (90 − 5) | **≈ 1,271 s ≈ 21 min** |
300	| Drain, normal working day | 1.75/s × 21,600 = 37,800 ÷ (90 − 1.75) | **≈ 7 min** |
301	| Drain, overnight | 0.1/s × 21,600 = 2,160 ÷ (90 − 0.1) | **≈ 24 s** |
302	| General drain time | minutes = 360 · r ÷ (90 − r) | r = 10 → 45 min; r = 20 → 1.7 h; r = 45 → 6 h; r ≥ 90 → never |
303	| 30 s while both are up | Webhooks are uncapped (ms). Outbound uses 5 of 90 req/s. | About 1 s. Breaks only above ~90 outbound edits/s sustained. |
304	| Safety-net catch-up, every 5 min | 5/s × 300 s = 1,500 changes | **1 call per run** |
305	| Full reconcile of all 5M | 5,000,000 ÷ 2,000 | **2,500 calls ≈ 28 s of cap** |
306	| History volume | ≈ 1.5 fields per edit × 10 edits/s | ≈ 15 rows/s at peak. Index `(record_id, field, occurred_at)`; partition later. |
307	
308	About 9× headroom over the assumed portal peak before draining takes as long as the outage
309	(45 edits/s). Portal edits/s is one of the numbers to watch, paged at 30/s ([Design](Design) §11).
310	A bulk update would break the 30 s target while it drains (≈ 9 min for 50,000 records), which is
311	why Q12 is a stated assumption.
312	
313	## Known limits
314	
315	- **Salesforce history during an outage is coarse.** A catch-up query returns the latest value
316	  and a record-level "last modified by/at". Intermediate Salesforce edits made during the
317	  outage aren't visible. Seeing them needs Salesforce's field-history API, which would be a
318	  further assumption.
319	- **Clocks.** Salesforce's `occurredAt` and our server clock are compared directly. We assume
320	  both are NTP-synced, with drift well below the gap between real edits.
321	
322	## Still open

325	  web process; the worker shares Postgres and Redis.
326	- Q11: how a webhook is authenticated before `apply()`.
327	- Q4: what a second portal user sees when the same field changes under them.

610	<section class="section reveal" id="background-and-scenario"><div class="wrap"><header class="section-head"><div class="kicker"><i class="ph ph-buildings" aria-hidden="true"></i></div><h2 class="heading-2">Background and scenario</h2></header><div class="section-body"><p class="body-3 measure">A client runs its sales team in Salesforce, a customer relationship management (CRM) product. Tequity has built the client an operations portal. Finance and customer-success staff work in the portal.</p><p class="body-3 measure">The same people exist in both places, as customers and as contacts. A sales person creates a customer in Salesforce. The portal should show that customer. A finance person on the portal then corrects the billing city. Salesforce should show the new city. Later, a sales person changes the phone number in Salesforce. The portal should show the new phone, and the city the finance person set should still be there.</p><p class="body-3 measure">The client also needs the history. They need to know who changed the phone, and who changed the city. The fact of an earlier edit stays on record after a later edit.</p><p class="body-3 measure">Salesforce stores its own copy. The portal stores its copy in PostgreSQL (Postgres). The two copies have to stay in sync. We are designing and building our side. Salesforce already exists, and it stays as it is.</p></div></div></section>
611	<section class="section reveal" id="the-systems-involved"><div class="wrap"><header class="section-head"><div class="kicker"><i class="ph ph-share-network" aria-hidden="true"></i></div><h2 class="heading-2">The systems involved</h2></header><div class="section-body"><p class="body-3 measure">Three parties matter.</p><ol class="cards cols-3 wide"><li><div class="body-3"><strong>Salesforce.</strong> The client's CRM. Sales users edit records here. Salesforce has its own database.</div></li><li><div class="body-3"><strong>The portal.</strong> Our application. Finance and customer-success users edit records here. Our database is Postgres.</div></li><li><div class="body-3"><strong>The network between them.</strong> Salesforce and the portal talk over the public internet, using Hypertext Transfer Protocol Secure (HTTPS). Each side keeps its own database. HTTPS is the only path between them.</div></li></ol><p class="title-3 measure">Who calls whom:</p><ul class="list list-ul measure"><li><div>When a record changes in Salesforce, Salesforce calls us. The call is a webhook: an HTTPS request to an endpoint we host. The webhook names the record and describes the change.</div></li><li><div>When a record changes in the portal, we call Salesforce. The call uses Salesforce's official record application programming interface (API): the create and update operations Salesforce already documents. The portal reaches Salesforce through that record API.</div></li><li><div>A sales user talks only to Salesforce. A portal user talks only to the portal. Neither user talks to the other system.</div></li></ul><p class="body-3 measure">The rate limit below applies to the requests we send to Salesforce. Webhooks Salesforce sends to us sit outside that cap.</p><div class="frame frame-diagram measure"><pre><code> Sales user                         Finance / customer-success user
612	     |                                          |

630	<section class="section reveal" id="requirements-and-scale"><div class="wrap"><header class="section-head"><div class="kicker"><i class="ph ph-list-checks" aria-hidden="true"></i></div><h2 class="heading-2">Requirements and scale</h2></header><div class="section-body"><p class="title-3 measure">Records:</p><ul class="list list-ul measure"><li><div>Customers and contacts. About these fields, and no others, for this exercise: customer name, status, and owner; contact full name, phone, email, city, owner, and the customer they belong to.</div></li><li><div><strong>5 million records</strong> in production, customers and contacts counted together.</div></li></ul><p class="title-3 measure">Sync:</p><ul class="list list-ul measure"><li><div>While both systems are up, a create or an update on either side is visible on the other side within <strong>30 seconds</strong>. Thirty seconds is the worst case. Everyday sync should land sooner.</div></li><li><div>Both sides may create. Both sides may update.</div></li><li><div>The current value of a field is the one we can justify. The earlier values, who made them, and when, stay on record. Dropping that history counts as losing a change.</div></li><li><div>An update we send to Salesforce must not bounce back and forth forever.</div></li></ul><p class="title-3 measure">Webhooks:</p><ul class="list list-ul measure"><li><div>Salesforce may deliver the same webhook twice.</div></li><li><div>Salesforce may deliver webhooks in a different order from the order of the edits.</div></li><li><div>Each webhook carries at least the fields in the sample below. <code>occurredAt</code> is the time Salesforce gives the event.</div></li></ul><p class="body-3 measure">The CRM API allows at most <strong>100 requests per second</strong>. That is our cap on calls to Salesforce. We choose how far under the cap to run.</p><p class="body-3 measure">We left the peak edit rate open. State the rate you assume, in edits per second, and use it in the arithmetic.</p><p class="body-3 measure">Sample webhook. This is enough to start. You may add fields. 36	both answer.
37	
38	### Worker
39	
40	The `worker` container runs two processes:
41	
42	- `manage.py rundramatiq --reload --reload-use-polling --processes 1 --threads 2`, which
43	  executes Dramatiq actors and restarts when a `.py` file under `src/` changes (`src/` is
44	  bind-mounted).
45	- `manage.py crontab` (dramatiq-crontab), which enqueues actors decorated with `@cron(...)` /
46	  `@interval(...)`. A Redis lock keeps it to one scheduler.
47	
48	If either process exits, the container exits and `restart: unless-stopped` brings both back.
49	`docker compose logs -f worker` shows a heartbeat line every minute when both are healthy.
50	
51	Put actors in `<app>/tasks.py`; both commands discover them automatically. After changing
52	dependencies, rebuild with `docker compose up -d --build worker`.
53	
54	All configuration comes from `.env` (see `.env.example`). Docker Compose reads the same file, so
55	the Postgres credentials and ports are defined once.
56
