1	# sync-data
2	
3	Two-way sync of customer and contact records between Salesforce (the client's CRM) and the
4	Tequity operations portal (Postgres). Salesforce calls us with webhooks; we call the Salesforce
5	record API from a background worker, with a target cap of 100 requests/sec (the cap is not built
6	yet). Design targets: 5 million
7	records, a 30-second sync window while both sides are up, and surviving a 6-hour Salesforce outage.
8	The brief is in [`docs/Round1.html`](docs/Round1.html).
9	
10	Status: phase 1 in progress. The models, admin, token authentication, URL layout and serializers
11	are built. No sync logic yet. The build plan and its checklist are in
12	[`docs/build-plan.md`](docs/build-plan.md).
13	
14	## Stack
15	
16	- Python 3.14, [uv](https://docs.astral.sh/uv/)
17	- Django 5.2 LTS, Django REST Framework (token authentication)
18	- Postgres 17 (portal database), Redis 7 (Dramatiq broker for the outbound worker)
19	- django-dramatiq, dramatiq-crontab (scheduler for `@cron` actors), django-environ
20	- psycopg 3 (Postgres driver)
21	- httpx (HTTP client for the Salesforce record API)
22	
23	## Prerequisites
24	
25	- uv 0.13+ (installs Python 3.14 for you)
26	- Docker with Docker Compose v2
27	
28	## Setup
29	
30	```sh
31	cp .env.example .env          # then set DJANGO_SECRET_KEY and POSTGRES_PASSWORD
32	uv sync                       # creates .venv and installs dependencies
33	docker compose up -d --build --wait   # Postgres, Redis and the worker
34	uv run python src/manage.py migrate
35	uv run python src/manage.py runserver
36	```
37	
38	The server listens on http://127.0.0.1:8000. `GET /api/v1/health/` returns 200 when Postgres and
39	Redis both answer.
40	
41	### API token for Salesforce
42	
43	Every API path starts with `/api/v1/` and every endpoint except health needs a token
44	(`Authorization: Token <key>`). To create the Salesforce integration user (group
45	`salesforce-integration`) and print its token:
46	
47	```sh
48	uv run python src/manage.py create_integration_user   # optional: --username <name>; safe to re-run
49	```
50	
51	Put the printed token in the webhook's `Authorization` header. Re-running reuses the same user
52	and token and prints the same key again.
53	
54	### Worker
55	
56	The `worker` container runs two processes:
57	
58	- `manage.py rundramatiq --reload --reload-use-polling --processes 1 --threads 2`, which
59	  executes Dramatiq actors and restarts when a `.py` file under `src/` changes (`src/` is
60	  bind-mounted).
61	- `manage.py crontab` (dramatiq-crontab), which enqueues actors decorated with `@cron(...)` /
62	  `@interval(...)`. A Redis lock keeps it to one scheduler.
63	
64	If either process exits, the container exits and `restart: unless-stopped` brings both back.
65	`docker compose logs -f worker` shows a heartbeat line every minute when both are healthy. The
66	heartbeat is dramatiq-crontab's own actor; the project has no actors yet.
67	
68	Put actors in `<app>/tasks.py`; both commands discover them automatically. After changing
69	dependencies, rebuild with `docker compose up -d --build worker`.
70	
71	All configuration comes from `.env` (see `.env.example`). Docker Compose reads the same file, so
72	the Postgres credentials and ports are defined once.

78	uv run pytest -q

201	   - if it's older, it stays in history only, marked *superseded*;
202	   - on an exact tie, Salesforce wins.

254	 5. Outbox     source = portal and a field was applied → INSERT outbox row
255	               source = salesforce → never
256	 6. COMMIT
257	```

260	
261	| Input | Webhook (A) | Portal save | Catch-up (C) |
262	|---|---|---|---|
263	| `event_id` | `eventId` | New UUID | `record_id` + Salesforce modified time |
264	| `occurred_at` | `occurredAt` | Our server clock when the save arrives | Salesforce modified time (record level) |
265	| `actor` | `changedBy` | The logged-in portal user | Salesforce "last modified by" |
266	| `fields` | Fields whose value differs from the last value we synced from Salesforce (the webhook carries the whole record, assumption Q2) | The fields in the form | Same comparison as a webhook |

268	## Sending and retries (path B)
269	
270	Decided ([Design](Design) §6, Q7). The **outbox** drives sending and retries; Dramatiq's own
271	retries are turned off for the outbound task.
272	
273	```
274	pending ──send──► sent ✓
275	   ▲  │
276	   │  ├─ unreachable / timeout / 5xx ─► pending again, next_attempt_at = now + backoff
277	   │  ├─ 429 slow down ───────────────► pending again, at Retry-After; the whole limiter slows
278	   │  └─ 400-type rejection ──────────► needs_review   (never dropped, alert raised)
279	   └── a person fixes it and requeues ◄─┘
280	```
281	
282	| Salesforce's answer | Action |
283	|---|---|
284	| Accepted | `sent`. On a create, store the Salesforce ID. |
285	| Unreachable, timeout, 5xx | Retry at 1, 2, 4, 8 s…, capped at 60 s. Four quick retries take 15 s, inside the 30 s target. |
286	| 429 slow down | Pause the shared limiter until `Retry-After`, halve its rate, then climb back by 5 req/s every 30 s to 90 |
287	| 400-type rejection | `needs_review` and an alert. Never dropped. |
288	| 401 / 403 | Stop all sending and page someone: our credentials are wrong |
289	
290	- **Outage detection:** after 5 consecutive unreachable failures, Salesforce is marked *down*.
291	  Sending stops and a probe runs every 10 s. When it succeeds, catch-up runs, then every pending
292	  row is due at once.
293	- **We send the current value, not the edit.** The worker reads the record's current values for
294	  the changed fields at send time. Pending edits to one record collapse into one call, and an
295	  update sent twice is harmless.
296	- **Workers claim rows** with `SELECT … FOR UPDATE SKIP LOCKED` and a lease (`lease_until`). If a
297	  worker dies mid-call, the lease runs out and another worker sends the row again.
298	- **Creates are upserts by external ID** (assumption Q13). Our record ID goes with the create, so a
299	  retry after a timeout matches the existing record instead of making a duplicate.
300	- **Wake-up:** Redis nudges the outbound task, and a timer task every 5 s backs up a lost nudge.
301	  Redis holds no pending calls, so losing its messages loses no work (Q8 closed).
302	
303	## How the brief's rules are met
304	
305	| Rule | Mechanism |
306	|---|---|
307	| Duplicate webhook | `change_event.event_id` is unique, so a repeat is a no-op. IDs are kept 7 days. |
308	| Out-of-order change | Per-field `occurred_at` comparison. The older change is kept in history but isn't current. |
309	| Different fields edited at once | The comparison is per field, so both edits survive |
310	| Same field edited at once | The newest `occurred_at` is current, and every edit stays in history. Two portal users: last save wins, with no warning (Q4). |
311	| History: who, what, when | `field_change` is written explicitly in `apply()` on every path, including superseded edits and bulk catch-up. It isn't a Django signal, because signals miss superseded edits and bulk writes. |
312	| Sync loop | Only portal edits create outbox rows. Our echo (actor = integration user) is never applied. |
313	| Pending calls survive restarts | The outbox row commits in the same transaction as the edit. Redis holds no pending calls, so losing a wake-up loses no work. |
314	| Slow down | A 429 pauses the shared limiter until `Retry-After`, halves its rate, then climbs back by 5 req/s every 30 s. The row stays pending. |
315	| Unreachable | Retry with backoff capped at 60 s. After 5 consecutive failures Salesforce is marked down, and a probe checks every 10 s. Nothing is dropped (Q9). |
316	| Rejected (bad data) | `needs_review` plus an alert; a person fixes and requeues it. Never dropped (Q9). |
317	| Webhooks missed in the outage | Catch-up (C), triggered by recovery and every 5 min |
318	
319	## After an outage
320	
321	1. Outbound calls start failing. After 5 consecutive failures Salesforce is marked down: sending
322	   stops, outbox rows stay pending, and a probe checks every 10 s whether Salesforce is back.
323	2. The probe succeeds, so Salesforce is back.
324	3. **Catch-up first.** Pull what changed in Salesforce since the watermark (minus a few minutes
325	   of overlap) and apply each record. Same-field conflicts are settled before we send anything.
326	4. **Then drain the outbox** at the full run rate. Edits to the same record are merged into one
327	   call.
328

174	## 5. Inbound path: webhook to our database
175	
176	Not built. Brief: "Our endpoint has to accept it, check it, and apply it before anything is
177	stored." Webhooks can arrive twice and out of order, and `occurredAt` is Salesforce's time for
178	the event.
179	
180	Decided. Steps 1 to 4 run before anything is stored. Step 5 is the first write.
181	
182	1. **Accept:** HTTPS `POST` to the webhook endpoint. The URL is `/api/v1/webhooks/salesforce/` (`openapi.yml`).
183	2. **Authenticate (Q11):** DRF `TokenAuthentication`. A missing or wrong token gets **401** and
184	   nothing is stored. The token belongs to a dedicated integration user, and a permission check
185	   limits that user to this endpoint.
186	3. **Validate:** a DRF serializer checks `eventId`, `recordId`, `objectType` (Customer or Contact),
187	   `occurredAt` (ISO 8601) and `changedBy`. Fields outside the brief's scope are ignored. A
188	   malformed payload gets **400** and nothing is stored.
189	4. **Work out what changed (Q2):** the webhook carries the whole record (assumption). A field
190	   counts as changed only if its value differs from the last value we synced from Salesforce.
191	5. **Apply:** `apply()` runs the duplicate, echo, ordering and history rules (§7 to §9) in one
192	   transaction.
193	6. **Respond 200** after the commit, also for a duplicate, so Salesforce stops redelivering it.
194	
195	The endpoint runs in the Django web process, separate from the worker (Q6).

197	## 6. Outbound path: portal edit to Salesforce API call
198	
199	Decided (Q7). Mechanism: [Architecture](https://github.com/hellosrijan/sync-data/wiki/Architecture), path B.
200	
201	**The outbox drives sending and retries.** A portal edit that applies at least one field adds an
202	outbox row in the same transaction (§9). Each row has `state`, `attempts`, `next_attempt_at`,
203	`last_error` and `lease_until`.
204	
205	```
206	pending ──send──► sent ✓
207	   ▲  │
208	   │  ├─ unreachable / timeout / 5xx ─► pending again, next_attempt_at = now + backoff
209	   │  ├─ 429 slow down ───────────────► pending again, at Retry-After; the whole limiter slows
210	   │  └─ 400-type rejection ──────────► needs_review   (never dropped, alert raised)
211	   └── a person fixes it and requeues ◄─┘
212	```
213	
214	Sending:
215	
216	- The Dramatiq outbound task is a single pass over due rows. Redis wakes it, and a timer task
217	  every 5 s backs up a lost wake-up. **Dramatiq's own retries are off for this task**, so no
218	  backoff of hours and no dead-letter set.
219	- Workers claim due rows with `SELECT … FOR UPDATE SKIP LOCKED` and set `lease_until`. If a worker
220	  dies mid-call, the lease runs out and another worker sends the row again.
221	- **We send the record's current value, not the edit.** The worker reads the current values of
222	  the changed fields at send time. So an older row can't overwrite a newer value in Salesforce,
223	  several pending edits to one record collapse into one call, and an update sent twice is
224	  harmless.
225	- **Creates carry our record ID as an external ID** and use upsert (assumption Q13). A create
226	  retried after a timeout then matches the existing record instead of making a duplicate. On
227	  success we store the Salesforce ID.
228	- Every call goes through the shared limiter at R = 90 req/s (Q10), retries included.
229	
230	Each answer from Salesforce:
231	
232	| Answer | Action |
233	|---|---|
234	| Accepted | `sent`. On a create, store the Salesforce ID. |
235	| Unreachable, timeout, 5xx | Back to `pending`. Retry at 1, 2, 4, 8 s…, capped at 60 s. Four quick retries take 1 + 2 + 4 + 8 = 15 s, inside the 30 s target. |
236	| 429 slow down | Back to `pending` at `Retry-After`. The shared limiter pauses until then, halves its rate, and climbs back by 5 req/s every 30 s to 90. |
237	| 400-type rejection | `needs_review` and an alert. Never dropped (Q9). A person fixes it and requeues. |
238	| 401 / 403 | Stop all sending and page someone. Our credentials are wrong, so every call would fail. |
239	
240	Salesforce is marked **down** after 5 consecutive unreachable failures. Sending stops and a probe
241	runs every 10 s. When the probe succeeds, catch-up runs, then every pending row is due at once
242	(§10).
243	
244	The outbox model is built (task 1.3.2). Not built yet: the outbound task, the limiter and the probe. The fields in an
245	outbound call are the fields the portal user changed, read at their current values.
246	`src/config/settings.py` already turns on Dramatiq's `Retries` middleware for every actor
247	(`max_retries` 20 by default). The outbound task must set `max_retries=0`.
248	
249	## 7. Rule: both sides change the same record
250	
251	Decided. Full mechanism: [Architecture](https://github.com/hellosrijan/sync-data/wiki/Architecture), `apply(change)`.
252	
253	- **Per field, the newest `occurred_at` wins.** On a webhook that's `occurredAt`. On a portal
254	  save it's our server clock when the save arrives (the portal sample has no time field), and
255	  the actor is the logged-in user (answers Q5).
256	- Each record stores the last-applied time and source of every field. A change is applied only
257	  if its `occurred_at` is newer than that field's stored time. Edits to different fields
258	  therefore both survive.
259	- **Every edit is written to the `field_change` history**, whether applied or superseded, inside
260	  the same transaction. It isn't a Django signal: signals miss superseded edits and bulk writes.
261	- Concurrent edits to one record are serialised with `SELECT ... FOR UPDATE`.
262	- **Exact tie: Salesforce wins.**
263	- **Two portal users, same field (Q4):** both saves apply, and the later one is current. There's no conflict check, so the earlier editor isn't warned. Both edits stay in history.
264	- *Assumption:* Salesforce's clock and ours are NTP-synced, with drift well below the gap between
265	  real edits. *If not:* a later real edit can be ranked as earlier and recorded as superseded.
266	
267	## 8. Rule: duplicate webhook, and an older webhook after a newer one
268	
269	Decided.
270	
271	- **Duplicate:** `change_event.event_id` is unique. The key is `eventId` for a webhook, a new
272	  UUID for a portal save, and `record_id` + Salesforce modified time for a catch-up result. A
273	  repeat hits the unique constraint, so we return OK and do nothing.
274	- **Dedupe retention: 7 days.** *Assumption:* Salesforce redelivers within 7 days. *If not:* a repeat
275	  that arrives after its ID has expired is not caught as a duplicate. The per-field time check still
276	  stops it from overwriting a newer value, but it adds a second history row.
277	- **Older after newer:** per field, an `occurred_at` older than the field's stored time is
278	  written to history as *superseded*. It never becomes the current value. The earlier edit stays
279	  on record, as the brief requires.
280	
281	## 9. Rule: stopping the sync loop
282	
283	Decided.
284	
285	- Only a **portal** change that applied at least one field creates an outbox row. Webhook and
286	  catch-up changes never do, so nothing received from Salesforce is ever sent back.
287	- **Our echo:** a webhook whose `changedBy` is our integration user is our own update coming
288	  back. It's recorded as a confirmation and never applied. This stops a delayed echo from
289	  overwriting a newer portal edit.
290	- *Assumption:* `changedBy` shows our integration user for writes made through the API. *If not:* our
291	  own echo is applied like any Salesforce change. It is still not sent back, because webhook changes
292	  never create outbox rows.
293	
294	## 10. The 6-hour outage
295	
296	Mechanism: [Architecture](https://github.com/hellosrijan/sync-data/wiki/Architecture), "After an
297	outage".
298	
299	What is on disk:
300	
301	| Item | Where | Note |
302	|---|---|---|
303	| Pending calls (portal edits not yet in Salesforce) | Postgres `outbox` | Committed in the same transaction as the edit. Survive any restart of ours. Never dropped (Q9). |
304	| Portal records and history | Postgres | Not affected by the outage. |
305	| Wake-up signal for the worker | Redis | Losing it loses no work; the outbox still holds every pending call. |
306	| Webhooks missed during the outage | Not on our disk | Recovered by the catch-up query (path C, assumption Q3). |
307	
308	How it drains:
309	
310	1. While Salesforce is down, outbound calls fail and their outbox rows stay pending. A probe
311	   checks every ~10 s whether Salesforce is back.
312	2. On recovery, catch-up runs first: it fetches what changed in Salesforce since the watermark and
313	   applies it. Same-field conflicts are settled before we send anything. Catch-up also runs every 5 min as a safety net (path C, Architecture).
314	3. Then the outbox drains at R = 90 req/s through the shared limiter. Several edits to one record
315	   are merged into one call.
316	
317	Retry policy (Q7, §6): the outbox drives retries at the limiter's pace, and no wait is longer
318	than 60 s. Dramatiq's backoff isn't used, so the drain figures below hold. Recovery is noticed
319	within 10 s (the probe). Catch-up then takes 54 calls, under 1 s, before the drain starts.
320	
321	Arithmetic. Symbols:
322	
323	- T = outage length = 6 h = 21,600 s.
324	- r = portal edits per second during the outage. **Assumed 5/s at peak (Q1).**
325	- R = run rate = **90 req/s (Q10)**, under the cap C = 100.
326	- B = backlog = r × T. One outbound call per edit (merging only makes it smaller).
327	
328	Worst case: the outage covers 6 hours of peak, and new edits keep arriving at r while we drain.
329	
330	- B = 5 × 21,600 = **108,000 calls**
331	- Catch-up first: 108,000 Salesforce-side changes ÷ 2,000 records per query = **54 calls**, < 1 s
332	- Drain: B ÷ (R − r) = 108,000 ÷ (90 − 5) = 108,000 ÷ 85 = **1,271 s ≈ 21.2 min**
333	
334	Other cases, same formula:
335	
336	| Case | r (portal edits/s) | Backlog B | Division | Drain |
337	|---|---|---|---|---|
338	| Worst case: 6 h of peak | 5 | 108,000 | 108,000 ÷ 85 | **21.2 min** |
339	| Normal working day | 1.75 | 37,800 | 37,800 ÷ 88.25 | **7.1 min** |
340	| Overnight (quiet hour) | 0.1 | 2,160 | 2,160 ÷ 89.9 | **24 s** |
341	
342	The r column is the portal share, half of the total in Q1. Working hours average 3.5 edits/s in
343	total, so 1.75 portal; the quiet hour is 0.2 in total, so 0.1 portal.
344	
345	Sensitivity: drain minutes = 21,600 · r ÷ (90 − r) ÷ 60 = 360 · r ÷ (90 − r).
346	
347	| r | Drain after 6 h at that rate |
348	|---|---|
349	| 5 (assumed) | 21 min |
350	| 10 | 45 min |
351	| 20 | 1.7 h |
352	| 45 | 6 h (as long as the outage) |
353	| ≥ 90 | never drains |
354	
355	The design has about 9× headroom over the assumed portal peak before draining takes as long as
356	the outage.
357	
358	Full reconcile, for comparison (Q3): 5,000,000 records ÷ 2,000 per query = 2,500 calls ÷ 90 req/s
359	≈ **28 s** of cap. Without a query API, one record per call: 5,000,000 ÷ 90 ≈ 15.4 h.
360
