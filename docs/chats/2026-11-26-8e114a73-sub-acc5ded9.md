187	  that are actually due), so calling it extra times is harmless.

190	
191	One Redis key, one Lua script (atomic token bucket), used by **every** caller: sends, retries,
192	the probe, and catch-up queries. Put it in `src/sync/limiter.py`.
193	
194	- State in Redis: current allowed rate (starts at `settings.SALESFORCE_RATE_LIMIT`) and a token
195	  count, refilled continuously.
196	- `limiter.acquire(timeout=...)` blocks (or the caller re-queues) until a token is free.
197	- On a 429: `limiter.throttle()` halves the current rate immediately, then a crontab job
198	  (`@interval(seconds=30)`) adds 5 req/s back, capped at the configured limit, until it's
199	  recovered.
200	- Test with `redis-py`'s real client against the Redis the compose stack already runs — no
201	  need to mock Redis for this.

204	
205	`SyncState` row `key="salesforce"`, `value={"status": "up"|"down", "consecutive_failures": N}`.
206	
207	- Every outbound failure classified as "unreachable" increments `consecutive_failures`; any
208	  success resets it to 0.
209	- At 5, set `status="down"`. While down, `send_outbound` should skip sending (checked at the
210	  top of the task) so it doesn't burn attempts against a Salesforce that's confirmed down.
211	- A separate crontab actor, `@interval(seconds=10)`, does a cheap probe call. On success:
212	  `status="up"`, `consecutive_failures=0`, then **run catch-up before anything else** (next
213	  section), then let `send_outbound` resume on its own next tick.

219	1. Read `SyncState.key="watermark"` (a timestamp); subtract a few minutes of overlap.
220	2. Query the Salesforce client for "changed since T", 2,000 records/page, through the limiter
221	   (6.1.1).
222	3. For each record returned, build a `Change(source="salesforce", event_id=f"{record_id}:{modified_at}", ...)`
223	   and call `apply()` (6.1.2). The echo check in `apply()` is **field-level** (compares each
224	   field's `sf_value`, same code path as a webhook) — don't add a record-level "skip if last

226	   the same record.
227	4. Advance the watermark to the latest `modified_at` seen **only after that page's transaction
228	   commits** (6.1.3) — so a crash mid-page re-reads the same page instead of skipping it.
229	5. Triggered by the probe's success (step above) and by a `@interval(minutes=5)` safety net
230	   (6.1.4). Both call the same function; it's idempotent because `apply()` already is.

87	def run_in_threads(jobs):
88	    """Start one thread per job behind a barrier. Each thread closes its own DB connection in a
89	    finally. Exceptions are collected and re-raised in the caller; nothing is swallowed."""
90	    barrier = threading.Barrier(len(jobs))
91	    results = [None] * len(jobs)
92	    errors = []
93	
94	    def runner(index, job):
95	        try:
96	            barrier.wait(timeout=10)
97	            results[index] = job()
98	        except BaseException as exc:  # collected, re-raised below
99	            errors.append(exc)
100	        finally:
101	            connection.close()
102	
103	    threads = [threading.Thread(target=runner, args=(i, job)) for i, job in enumerate(jobs)]
104	    for thread in threads:
105	        thread.start()
106	    for thread in threads:
107	        thread.join(timeout=30)
108	    assert not any(t.is_alive() for t in threads), "apply() hung: possible deadlock"
109	    if errors:
110	        raise errors[0]
111	    return results

174	## 5. Inbound path: webhook to our database
175	
176	Not built. Brief: "Our endpoint has to accept it, check it, and apply it before anything is
177	stored." Webhooks can arrive twice and out of order, and `occurredAt` is Salesforce's time for
178	the event.
179	
180	Decided. Steps 1 to 4 run before anything is stored. Step 5 is the first write.
181	
182	1. **Accept:** HTTPS `POST` to the webhook endpoint. The URL is `/api/v1/webhooks/salesforce/` (`openapi.yml`).
183	2. **Authenticate (Q11):** DRF `TokenAuthentication`. A missing or wrong token gets **401** and
184	   nothing is stored. The token belongs to a dedicated integration user, and a permission check
185	   limits that user to this endpoint.
186	3. **Validate:** a DRF serializer checks `eventId`, `recordId`, `objectType` (Customer or Contact),
187	   `occurredAt` (ISO 8601) and `changedBy`. Fields outside the brief's scope are ignored. A
188	   malformed payload gets **400** and nothing is stored.
189	4. **Work out what changed (Q2):** the webhook carries only the changed fields (assumption,
190	   matches the brief's sample). A field counts as changed only if its value differs from the
191	   last value we synced from Salesforce — the same comparison that makes the rule correct even
192	   if a webhook ever carries the whole record instead.
193	5. **Apply:** `apply()` runs the duplicate, echo, ordering and history rules (§7 to §9) in one
194	   transaction.
195	6. **Respond 200** after the commit, also for a duplicate, so Salesforce stops redelivering it.
196	
197	The endpoint runs in the Django web process, separate from the worker (Q6).

199	## 6. Outbound path: portal edit to Salesforce API call
200	
201	Decided (Q7). Mechanism: [Architecture](https://github.com/hellosrijan/sync-data/wiki/Architecture), path B.
202	
203	**The outbox drives sending and retries.** A portal edit that applies at least one field adds an
204	outbox row in the same transaction (§9). Each row has `state`, `attempts`, `next_attempt_at`,
205	`last_error` and `lease_until`.
206	
207	```
208	pending ──send──► sent ✓
209	   ▲  │
210	   │  ├─ unreachable / timeout / 5xx ─► pending again, next_attempt_at = now + backoff
211	   │  ├─ 429 slow down ───────────────► pending again, at Retry-After; the whole limiter slows
212	   │  └─ 400-type rejection ──────────► needs_review   (never dropped, alert raised)
213	   └── a person fixes it and requeues ◄─┘
214	```
215	
216	Sending:
217	
218	- The Dramatiq outbound task is a single pass over due rows. Redis wakes it, and a timer task
219	  every 5 s backs up a lost wake-up. **Dramatiq's own retries are off for this task**, so no
220	  backoff of hours and no dead-letter set.
221	- Workers claim due rows with `SELECT … FOR UPDATE SKIP LOCKED` and set `lease_until`. If a worker
222	  dies mid-call, the lease runs out and another worker sends the row again.
223	- **We send the record's current value, not the edit.** The worker reads the current values of
224	  the changed fields at send time. So an older row can't overwrite a newer value in Salesforce,
225	  several pending edits to one record collapse into one call, and an update sent twice is
226	  harmless.
227	- **Creates carry our record ID as an external ID** and use upsert (assumption Q13). A create
228	  retried after a timeout then matches the existing record instead of making a duplicate. On
229	  success we store the Salesforce ID.
230	- Every call goes through the shared limiter at R = 90 req/s (Q10), retries included.
231	
232	Each answer from Salesforce:
233	
234	| Answer | Action |
235	|---|---|
236	| Accepted | `sent`. On a create, store the Salesforce ID. |
237	| Unreachable, timeout, 5xx | Back to `pending`. Retry at 1, 2, 4, 8 s…, capped at 60 s. Four quick retries take 1 + 2 + 4 + 8 = 15 s, inside the 30 s target. |
238	| 429 slow down | Back to `pending` at `Retry-After`. The shared limiter pauses until then, halves its rate, and climbs back by 5 req/s every 30 s to 90. |
239	| 400-type rejection | `needs_review` and an alert. Never dropped (Q9). A person fixes it and requeues. |
240	| 401 / 403 | Stop all sending and page someone. Our credentials are wrong, so every call would fail. |
241	
242	Salesforce is marked **down** after 5 consecutive unreachable failures. Sending stops and a probe
243	runs every 10 s. When the probe succeeds, catch-up runs, then every pending row is due at once
244	(§10).
245	
246	The outbox model is built (task 1.3.2). Not built yet: the outbound task, the limiter and the probe. The fields in an
247	outbound call are the fields the portal user changed, read at their current values.
248	`src/config/settings.py` already turns on Dramatiq's `Retries` middleware for every actor
249	(`max_retries` 20 by default). The outbound task must set `max_retries=0`.
250	
251	## 7. Rule: both sides change the same record
252	
253	Decided. Full mechanism: [Architecture](https://github.com/hellosrijan/sync-data/wiki/Architecture), `apply(change)`.
254	
255	- **Per field, the newest `occurred_at` wins.** On a webhook that's `occurredAt`. On a portal
256	  save it's our server clock when the save arrives (the portal sample has no time field), and
257	  the actor is the logged-in user (answers Q5).
258	- Each record stores the last-applied time and source of every field. A change is applied only
259	  if its `occurred_at` is newer than that field's stored time. Edits to different fields
260	  therefore both survive.
261	- **Every edit is written to the `field_change` history**, whether applied or superseded, inside
262	  the same transaction. It isn't a Django signal: signals miss superseded edits and bulk writes.
263	- Concurrent edits to one record are serialised with `SELECT ... FOR UPDATE`.
264	- **Exact tie: Salesforce wins.**
265	- **Two portal users, same field (Q4):** both saves apply, and the later one is current. There's no conflict check, so the earlier editor isn't warned. Both edits stay in history.
266	- *Assumption:* Salesforce's clock and ours are NTP-synced, with drift well below the gap between
267	  real edits. *If not:* a later real edit can be ranked as earlier and recorded as superseded.
268	
269	## 8. Rule: duplicate webhook, and an older webhook after a newer one
270	
271	Decided.
272	
273	- **Duplicate:** `change_event.event_id` is unique. The key is `eventId` for a webhook, a new
274	  UUID for a portal save, and `record_id` + Salesforce modified time for a catch-up result. A
275	  repeat hits the unique constraint, so we return OK and do nothing.
276	- **Dedupe retention: 7 days.** *Assumption:* Salesforce redelivers within 7 days. *If not:* a repeat
277	  that arrives after its ID has expired is not caught as a duplicate. The per-field time check still
278	  stops it from overwriting a newer value, but it adds a second history row.
279	- **Older after newer:** per field, an `occurred_at` older than the field's stored time is
280	  written to history as *superseded*. It never becomes the current value. The earlier edit stays
281	  on record, as the brief requires.
282	
283	## 9. Rule: stopping the sync loop
284	
285	Decided.
286	
287	- Only a **portal** change that applied at least one field creates an outbox row. Webhook and
288	  catch-up changes never do, so nothing received from Salesforce is ever sent back.
289	- **Our echo:** a webhook whose `changedBy` is our integration user is our own update coming
290	  back. It's recorded as a confirmation and never applied. This stops a delayed echo from
291	  overwriting a newer portal edit.
292	- *Assumption:* `changedBy` shows our integration user for writes made through the API. *If not:* our
293	  own echo is applied like any Salesforce change. It is still not sent back, because webhook changes
294	  never create outbox rows.

## `apply(change)`: one function for every inbound change

Webhooks (A), portal saves and catch-up results (C) all go through `apply()`. One
implementation covers duplicates, ordering, history and the loop rule.

```
change = { source: salesforce | portal, event_id, record_id, occurred_at, actor, fields{...} }

one Postgres transaction:
 1. Dedupe     INSERT event_id INTO change_event (unique). Conflict → duplicate: return OK.
 2. Lock       SELECT record ... FOR UPDATE   (serialises concurrent edits to one record)
 3. Echo       source = salesforce and actor = our integration user → our own update coming
               back: record it as a confirmation, apply nothing, stop.
 4. Per field  always INSERT field_change(record, field, value, actor, occurred_at, source)
               occurred_at > field's stored time → becomes current          (applied)
               otherwise → stays in history only                            (superseded)
               exact tie → Salesforce wins
 5. Outbox     source = portal and a field was applied → INSERT outbox row
               source = salesforce → never
 6. COMMIT
```

Where the inputs come from:

| Input | Webhook (A) | Portal save | Catch-up (C) |
|---|---|---|---|
----
### 4. What happens inside `apply()`

The box says *dedupe · lock · history · per-field newest wins · outbox*. In order:

1. **Dedupe:** try to record the change's ID. If it's already there, this is a duplicate, so reply OK and stop.
2. **Lock** the record, so two simultaneous edits to it go one after the other instead of overwriting each other.
3. **Echo check:** if the change came from Salesforce and its `changedBy` is *our integration user*, it's our own update coming back. Record it and stop.
4. **For each field:**
   - always write a history row;
   - if the change is newer than that field's stored time, make it the current value;
